# 05-实测记录 · Pi 0.99.2 codemode vs direct 对照

> 日期：2026-10-01　机器：MacBook Pro M5 Pro / 48GB（Apple Silicon）
> 结论先行：**codemode 的成本是固定的，direct 的成本是线性的。交叉点在 8 个工具左右。**

---

## 一、为什么要自己跑

Mario 反 MCP 那篇文章的数字是 2025-11 的（Playwright 21 工具 13.7k tokens），Pi 官宣 codemode 时**一个 benchmark 都没给**。公开渠道能找到的唯一 Pi codemode 对照是 withone.ai 的 n=1 实测。

所以这个选题要么自己跑，要么就只能写"我核实"不能写"我实测"。我选择自己跑。

## 二、实验环境（可复现）

| 项 | 值 |
|---|---|
| Pi | `@earendil-works/pi-coding-agent` **0.99.2**（npm tarball 解包直读 CHANGELOG 确认） |
| Node | 22.22.2（托管版） |
| 模型 | **Ollama 0.34.1 + qwen3.8:27b-mlx**（本地，127.0.0.1:11434/v1），`--thinking off` |

**为什么用 mock server 而不是真 server**：
1. 可复现——工具数、描述长度完全可控，别人照着能跑出一样的曲线；
2. 不依赖网络安装包；
3. 能画出 scaling 曲线，真实 server 工具数固定，做不出曲线。

## 三、实验设计（三个决定成败的取舍）

**取舍一：用最简 prompt，不测任务完成度。**
每轮只发一句 `Reply with the single word: OK`。这样测的就是**「光把工具挂上要吃掉多少 token」**，不依赖本地 27B 模型能不能写好 JS 编排。指标干净、可重复。

**取舍二：必须处理 prompt cache 干扰。** ⚠️ 这是最容易做出假数据的地方。
第一次跑的时候，20-codemode 和 60-codemode 的 prompt 前缀一模一样（codemode 下工具根本不进声明），第二次跑几乎全部命中缓存——`input=5, cacheRead=10214`。只看 `input` 会得出"60 个工具只要 5 个 token"的荒谬结论。

**解法**：每组用 `--append-system-prompt bench-nonce-<随机8位>`，强制前缀不同，缓存必然失效。
**指标统一取 `prompt = input + cacheRead`**（实际送进模型的 token 总量）。

**取舍三：耗时数据不可用，只能看 token。**
同样是 20 个工具，direct 第一轮 386.8s、60 个工具那轮 134s——本机同时还在跑别的东西，MLX 负载不稳。**耗时只作参考，不进结论。**

| 组 | v1 | v2 | 偏差 |

| 20-codemode | 10,235 | 10,240 | 5 |

|---|---|---|
| 20-codemode | **0 次** | 36 次 |
| 20-direct | **3 次** | **0 次** |

codemode 下工具名一次都没出现在发给模型的请求里；direct 下完整声明。这跟官方 `docs/mcp.md` 写的完全一致，不是我推断的。

## 五、三个结论

### 结论一：codemode 是固定成本，direct 是线性成本

- **codemode**：20 个工具 10,240 → 60 个工具 **10,239**。工具数翻 3 倍，**prompt 只差 1 个 token**。
- **direct**：20 个工具 14,018 → 60 个工具 **26,216**。翻 3 倍工具，**涨了 87%**。

拟合一下，direct 的单工具边际成本：
```
(26,216 − 14,018) ÷ 40 = 304.95 ≈ 305 tokens / 工具
```
回代检验（四个点全部对上）：

| n | 公式 7,926 + 305n | 实测 | 误差 |
|---|---|---|---|
| 5 | 9,451 | 9,448 | 3 |
| 10 | 10,976 | 10,967 | 9 |
| 20 | 14,026 | 14,018 | 8 |
| 60 | 26,226 | 26,216 | 10 |

**四个点误差都在 0.1% 以内。** 这不是拟合凑数，是硬碰硬对上了。

### 结论二：codemode 不是免费的，它有 2,314 tokens 的固定开销

基线（不接任何 MCP server）是 7,926，接上 20 个工具的 codemode 变成 10,240。
这 **+2,314 tokens 是 codemode 工具自身的描述 + 系统提示里的 `mcp_servers` 段**，跟接多少工具无关。

**这条必须写进文章。** 很多报道把 codemode 说成"零成本发现机制"，不对——它是**把随工具数线性增长的成本，换成了一笔固定租金**。这个说法才准确，也更经得起追问。

### 结论三：官方没给的临界点，我算出来了

Pi 官方文档只说 `direct` 适合"小、高频工具集"，没给数。用上面的数据能算：

```
codemode 固定开销 2,314 ÷ 单工具 305 ≈ 7.6
```

**临界点约 8 个工具**：工具数 ≤ 7，direct 反而更省；≥ 8，codemode 才划算。

**实测验证闭环**：
- n=5：direct 9,448 < codemode 10,240 → **direct 更省** ✅
- n=10：direct 10,967 > codemode 10,240 → **codemode 更省** ✅

临界点确实落在 5 和 10 之间，跟算出来的 7.6 一致。**预测和实测对上了。**

⚠️ **这个 8 是本机 mock server 的数字**（单工具描述 900 字符 ≈ 305 tokens）。真实场景要按
`临界点 = 2314 ÷ 单工具 token 数` 自己算。但**公式是通用的**，而且这个"存在一个临界点"的判断本身，比具体数字更重要——它把 Pi 那句"小工具集用 direct"从经验之谈变成了可计算的决策。

## 六、🔥 prompt cache 打穿实验（本轮最有价值的一组）

前面几组测的是"占多少 token"，这一组测的是**"会不会把缓存打穿"**——也就是我在官方 `docs/mcp.md` 里读到的那条隐藏约束。

**设计**：同一 session 连续四轮，前三轮 codemode 不变，第四轮只改 exposure 为 direct，别的什么都不动。

**数据**：

| 轮 | exposure | 新算 tokens（input） | 缓存命中（cacheRead） | 该轮耗时 |
|---|---|---|---|---|
| r1 | codemode | 422 | 10,515 | 97.8s |
| r2 | codemode | **19** | 10,985 | 22.4s |
| r3 | codemode | **19** | 11,039 | **2.3s** |
| **r4** | **direct** | **14,763** | **113** ⬇️ | **57.4s** |

**这组数字说了三件事：**

1. **codemode 下，多轮对话几乎零新增成本。** 到 r3，一万多 token 的 prompt 里只有 **19 个是新算的**，其余全部命中缓存。代价就是 r3 的耗时从 97.8s 一路降到 **2.3s**。

2. **只改一个 exposure 配置，缓存当场全废。** cacheRead 从 **11,039 崩到 113**——命中率从 99.8% 掉到 0.8%。同一轮耗时从 2.3s 变回 57.4s，**差 25 倍**。

3. **这解释了 Pi 为什么要给 exposure 分档。** 官方说 `direct` 适合"小、高频工具集"，现在有了机制层面的解释：不是因为小工具省 token，而是因为**工具声明住在请求前缀里，前缀一动，前面攒的缓存全废**。高频调用的工具放 direct，是为了让它稳定待在前缀里别动。

⚠️ 说明：r1 的 cacheRead 就有 10,515，是因为前面几组实验已经把系统提示前缀缓存住了。这不影响结论——要看的是 **r3 → r4 的崩塌**，这是同一次会话内的前后对照。

**这一条目前中英文报道都没有，是本轮实测最值钱的产出。**

## 七、方法的局限（写文章时必须自己先说）

1. **模型是本地 27B，不是 Claude/GPT。** token 计数与模型无关，所以 prompt 侧结论成立；但**"模型能不能用好 codemode"这一侧完全没测**——本地模型能力不足以做这个判断。文章里不能把这组数据说成"codemode 让任务完成得更好"。
2. **工具描述是模拟的。** 900 字符/工具是我设定的，真实 server 差异很大（Mario 实测 Playwright 是 ~652 tokens/工具）。**绝对数字不能直接套用，只能引用趋势和公式。**
3. **Ollama 的 prompt cache 机制和云厂商不同。** 云上 cacheRead 通常是打折计费的，本机不打折。所以"省 token"≠"省钱"，文章里别混着说。
4. **n=1 per config。** 虽然 v1/v2 偏差 <0.05%，但严格讲每组只跑了一次。

## 八、复现步骤

```bash
# 1. 装 Pi（沙箱里 npm 会静默失败，用独立 cache + 新目录）
mkdir -p ~/pi-bench/fresh && cd ~/pi-bench/fresh
echo '{"name":"bench","version":"1.0.0"}' > package.json
npm install @earendil-works/pi-coding-agent --ignore-scripts --no-audit --no-fund --cache /tmp/pi-npm-cache

# 2. 配本地模型 ~/.pi/agent/models.json
#    baseUrl 必须写 127.0.0.1，本机 localhost 有 ::1 映射坑

# 3. 启动 mock server（本目录 server.js），写入 ~/.pi/agent/mcp.json
#    TOOL_COUNT 控制工具数，exposure 控制档位

# 4. 跑（注意 --append-system-prompt 的 nonce 不能省）
node .../cli.js --model ollama/qwen3.8:27b-mlx --thinking off --no-session \
  --mode json --append-system-prompt "bench-nonce-XXXXXXXX" -p "Reply with the single word: OK"

# 5. 取最后一个 role=assistant 的 message_end 的 usage，prompt = input + cacheRead
```

脚本在本文材料目录：`run-bench2.js`（对照）、`run-cache-test.js`（缓存）、`server.js`（工具源）。汇总读数在 `data/`。

## 九、补测：低 n 区的 codemode（2026-10-01，四视角审校后）

**为什么补**：成稿第一版拿 n=20 的 codemode 读数（10,240）去跟 n=5 的 direct 比，得出「临界点约 8 个工具」。审校指出这是**把推断当实测**——n=5 和 n=10 的 codemode 压根没跑。这个洞不补，临界点就是悬空的。

**结果（加 nonce 冷启动，同 v2 方法）**：

| 工具数 | codemode | input | cacheRead | direct（v2 已有） |
|---|---|---|---|---|
| 5 | **10,239** | 10,237 | 2 | 9,448 |
| 10 | **10,238** | 6,412 | 3,826 | 10,967 |

**三个收获：**

1. **平线从 n=5 就成立。** 四个点 10,239 / 10,238 / 10,240 / 10,239，最大偏差 2 tokens，落在 nonce 抖动的量级里。codemode 是水平线这件事不再只靠 20/60 两个点撑着。

2. **临界点被实测两侧夹住了。** n=5 时 direct（9,448）比 codemode（10,239）省；n=10 时 direct（10,967）比 codemode（10,238）贵。交叉确实发生在 5 到 10 之间，跟公式算的 7.6 对上。**这是从「算出来的」变成「量出来的」。**

3. **固定租金据实改为 2,313**（10,239 − 7,926），此前按 10,240 记的 2,314 是单点值。临界点 `2,313 ÷ 305 = 7.58`，按 Mario 实测的真实描述长度（约 652 tokens/工具）重算 `2,313 ÷ 652 = 3.55`。

**仍未闭环的（写文章时必须自己说）**：
- 只测了**同一个 server 内**工具数变化，未测多 server 并联（每个 server 在系统提示里占一个命名空间条目，增长机制不同）。
- ~~耗时仍未分离一次性代价与稳态代价（没跑 direct 的第二轮）。~~ **已在第十节闭环。**
- 任务侧效果未测。

## 十、r5 / r6：direct 的第二、第三轮（2026-10-01，同日）

**为什么补**：3.2 里 r4 那个 14,763 到底是「改配置那一下的一次性打穿」还是「之后每轮都要付的稳态代价」，当时没法分离。补两轮同配置连续跑即可判定。

**怎么绕过去的（关键）**：前六次尝试全部卡在同一个错上，见 `04-踩坑与复盘.md` 第〇节与第五节。最后的有效解是环境变量绕开 credential store：

```bash
# OPENAI_API_KEY 是占位值：ollama 本地推理不校验 key，只要这个变量存在即可；
# 你自己的环境有真 key 就换上去，或者干脆把这一项删掉。
PI_CODING_AGENT_DIR=/tmp/pi-agent-r5 PI_KEY_ENV=1 OPENAI_API_KEY=dummy \
  node .../pi-coding-agent/dist/bundle/cli.js \
  --model ollama/qwen3.8:27b-mlx --thinking off \
  --session-dir /tmp/pi-cache-session --mode json --continue \
  -p "Reply with the single word: FIFTH"
```

`PI_KEY_ENV=1` 让 key 从环境走，不再碰 credential store，`auth.json.lock` 的 mkdir 竞态就消失了。**这一条是后面所有复现的前置。**

**数据**（r5 / r6 与 r4 配置完全相同，只有那一句 prompt 不同）：

| 轮 | exposure | 新算 tokens（input） | 缓存命中（cacheRead） |
|---|---|---|---|
| r4 | direct | 14,763 | 113 |
| r5 | direct（第二轮） | **11,139** | 2 |
| r6 | direct（第三轮） | **11,184** | 0 |

**判定：一次性 / 稳态 已分离。**

- r5 与 r6 差 **45（0.4%）**，两轮都落在一万一。这不是巧合，是稳态。
- 也就是说：**direct 打穿缓存不是改配置那一下的余波，是之后每一轮都要付的账。** r4 的 14,763 里含一次性的那部分（首次把工具声明灌进前缀），但底下垫着的 1.1 万是后续躲不掉的。
- 对照 codemode：r2 新算 19、r3 新算 19，稳态两个百分点都不动。**同一个 session，codemode 稳态 19，direct 稳态一万多，差三个数量级。**

**两条必须自己说的口径**：

1. **r6 对 r5 的缓存零命中**（cacheRead=0），我没查清 Ollama 在本机按什么规则保留前缀缓存（可能是 TTL，也可能只留最后一段）。所以正文不解释这个数字，只取「r5、r6 两次读数贴得极近」这个事实——判定稳态用两次独立读数的一致性，不依赖命中率机制。
2. **r5 是冷启动读数。** 补测中间被 credential 锁卡了约四十分钟，本机缓存早已过期（r5 input 11,139 ≈ 整个 prompt 长度，符合冷启动特征）。这不影响 r5/r6 对照——那两轮紧挨着跑完，中间没隔。

**仍未闭环**：多 server 并联、任务侧效果。
